# A/B 双机交接协议

## 1. 同步与基线核验

1. 用户授权 A、B 通过 Git 提交和推送本轮测试计划、测试结果及必要的交接信息，无需用户中转。仅提交本轮负责的文件，不切换分支、覆盖其他改动或泄露密码和密钥。
2. 两机须对齐上一轮修复。仅获取计划文档不等于获取修复。使用提交共享代码时先检查提交范围，不包含无关修改或敏感文件；同步后双方核对分发提交及源码指纹。
3. 两机在仓库根目录执行以下只读命令，将提交号和工作区文件清单记入各自结果文件；不要将命令输出中的敏感内容写入结果。

   ```powershell
   git branch --show-current
   git rev-parse HEAD
   git status --short
   ```

4. 对涉及本轮基线的已修改及新建源码文件，双方逐一执行 `Get-FileHash -Algorithm SHA256 -LiteralPath '相对或绝对文件路径'`，交换文件路径和 SHA-256，确认内容相同。只对源码及测试文件操作，不读取或传播配置中的秘密。计划、各自结果及其他双方独有的记录文件不算源码差异。
5. 两机记录操作系统、应用构建方式、浏览器及版本、真实移动设备及浏览器、测试服务标识、时区和网络条件。不记录带参数的凭证 URL。测试服务、代码指纹或平台能力不一致时标记阻塞，不能拿不同版本互相判定。
6. A 建立本轮编号，如 `E2E-YYYYMMDD-01`；B 确认收到。基线变更后重新记录指纹和轮次；未经对方同步，不用新旧版本的结果作跨端结论。

## 2. 文件所有权和 Git 同步

- A 独占编辑 `results-a.md` 与 `issues.md`；B 独占编辑 `results-b.md`。双方不要同时写同一文件。用例定义和交接文件由 A 维护，B 通过自己的结果提出修改建议。
- 双方自行同步 `origin/master` 上的交接，不需要用户转发。每次先检查 `git status --short --branch`，获取远端后检查提交范围；只在安全时快进。仅把已提交并推送的记录视为对方可读取。
- Git 是异步信令，不代表对方已看到消息。双方在各自结果文件中写入轮次、实例、状态、动作及下一位负责人，并提交推送；接收方定期检查远端、同步后读取并确认。没有对方对具体实例的明确就绪记录时，不执行双机动作。私聊可用后，协调消息也必须包含 AI 测试助手身份、测试目的和轮次。
- 为减少竞争，同一轮交接由发送方推送后把写入机会交给接收方；接收方先同步，再只编辑自己的结果文件并推送。若推送被拒、工作区有冲突或远端包含意外源码变更，先检查并保留双方数据，禁止强推、重置或覆盖；无法安全合并时记录阻塞。
- 同一结果文件若出现冲突，暂停并分别保留双方原始记录，由文件所有者根据用例 ID 合并；不使用强制推送或覆盖别人的记录。

## 3. 双人用例运行协议

1. **准备：** A 公布用例 ID、端组合、发送方、合成测试数据标识和前置条件；B 确认相同基线、测试服务和安全范围。需要测试群时先验证群里只有 A/B。
2. **就绪：** 各自在目标端登录，确认当前账号和会话，并由 B 明确回复“就绪”。接收端保持对应页面或按用例要求切后台/离线。
3. **执行：** 只有指定发起者执行一次操作；AI 操作者的消息正文示例：`[轮次/用例ID] 我是 AI 测试助手，正在进行双机端到端测试，无需回复。` 人工操作者注明其真实身份和测试目的。不包含密码、真实用户内容或私人数据。
4. **确认：** 各自记录操作时间、服务响应或客户端状态、接收端实际内容及显示时间。同步消息、上传文件和通话以接收方实际观察为准；本地乐观显示不能证明服务端成功。
5. **记录：** A、B 在各自文件中以相同的“轮次 + 用例 ID + 端组合 + 方向”记录；发生异常各自记录，A 汇总到问题表。时钟未同步时只记观察时间，不计算精确跨机延迟。
6. **收尾：** 按用例清理本轮测试对象并恢复设置，双方确认。不得删除不属于本轮的数据。重新测试使用新的实例标识，避免旧消息被误认为本次结果。

## 4. 端组合和结果判定

`D` 为 Windows 桌面应用，`W` 为桌面浏览器，`M` 为真实移动浏览器。用例中的 `A端/B端` 表示 A 和 B 各自使用的端，不表示发送方向。

- 本地类 `L`：A、B 各在 D、W、M 执行一次；仅标明单端的用例按用例范围执行。不可操作的设备记阻塞。
- 双人类 `P`：依次执行 `D/D`、`D/W`、`W/D`、`W/W`、`D/M`、`M/D`、`W/M`、`M/W`；每一组合先 A 发起/B 接收，再交换方向。一个组合只需一台真实手机，轮换给相应角色。若用例明确要求 `M/M`，则需两台真实手机；缺少设备记阻塞。
- 双人类的发送方和接收方必须分别记录结果。若只观察到一侧，另一侧为未执行或阻塞，整体不能算通过；服务端是否返回成功和刷新后是否保持按用例单独核对。
- 手机设备不能同时由两人各自控制时，通过线下安全交接完成角色切换，重新核对账户；不能仅靠桌面浏览器切窄窗口冒充真机。
- 测试时长、传输耗时和重试次数应实际记录。除非项目有明确契约，不把自定的响应秒数当成产品合格阈值；明显无法完成时记录失败或阻塞及依据。

## 5. 停止条件与恢复

出现持续 502、请求超时、WebSocket 断连或登录异常时，记录端、用例、脱敏时间和状态；可对相同测试数据重复一次观察并标注重试，但不得对写请求盲目自动重试。先区分本机、代理及测试服务的现象，无法确认根因时标记“原因待定位”。系统网络模拟不得影响其他用户或正在运行的无关工作；无法安全隔离则记阻塞。

不得因服务不稳定而将未跑用例判为通过，也不能提前开始修复。恢复后用相同基线继续；如需要改代码才能恢复环境，先报告用户，等待用户明确调整“完成测试后修复”的规则。
