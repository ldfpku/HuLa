# SMJ 双机全功能端到端测试

## 开始前先读

本计划用于两个测试账户、两台电脑协作验证同一测试环境。先阅读 [双机交接](handoff.md)，然后按 [测试用例](test-cases.md) 执行。A 和 B 分别填写 [A 的结果](results-a.md) 和 [B 的结果](results-b.md)；A 负责汇总 [问题记录](issues.md)。

邮箱内嵌、待办、在线状态和非最大化窗口的发布后人工专项复测，请参阅 [人工专项测试清单](manual-release-checklist.md)。该清单不替代完整功能测试。

| 角色 | 账户 | 主要职责 | 写入文件 |
| --- | --- | --- | --- |
| A | `test@smjtools.com` | 本机执行、组织双人用例、汇总问题和复测 | `results-a.md`、`issues.md` |
| B | `test-smj@smjtools.com` | 另一台电脑执行、配合双人用例、反馈问题 | `results-b.md` |

账户密码由用户安全提供，不保存在本目录。两台电脑分别操作自己的账户；不能假定对方已经在线或任务已完成。

## 范围和安全边界

- 必测端为 Windows Tauri 桌面端（D）、桌面浏览器 Web（W）及真实移动浏览器 Web（M）。移动视口模拟可作为辅助证据，但不能代替 M 的真机结果。
- 桌面与 Web 是不同运行方式；浏览器中的桌面样式不能算桌面原生。原生 Android/iOS、macOS 和 Linux 不在本轮范围。
- 仅操作上述两个测试账户及测试开始后由双方创建的数据，包括仅含 A/B 的私聊、双人测试群、测试文件和测试消息。不得使用全员群或已有真实群代替测试群，不得联系第三人。
- 双方消息、测试文件和测试群均注明执行者真实身份、双机端到端测试目的和本轮编号。AI 操作者注明“AI 测试助手”，必要时注明“无需回复”。位置只使用模拟坐标；截图、共享屏幕、邮件与文件仅包含合成测试内容。
- 删除、撤回、退出、清除等操作只针对本轮创建的对象。好友关系、个人资料、通知、主题、快捷键和系统权限须先记录初始状态，结束后恢复；如不能安全恢复，停止并记录阻塞。
- 只使用免费且已授权的服务和设备权限；不得提交个人凭据或将私人信息、真实聊天、邮件、截图发送到外部服务。需要付费、第三账户、额外权限、不可用设备或特殊管理员权限时记为阻塞。
- 仓库、结果文件、控制台摘录和附件中不得出现密码、令牌、登录链接、带凭证的 URL、真实用户资料或未脱敏的截图。证据使用安全可访问的脱敏摘要或引用；不要将其他人不可访问的本地临时路径冒充共享证据。

## 测试基线和启动

两台机器必须先核对同一源码基线、上一轮修复及测试服务。只同步本计划文件**不会**让另一台机器自动获得修复，必须同时同步源码和测试文件。在两机完成核验前，不执行或判定跨机比较。详见 [交接协议](handoff.md#1-同步与基线核验)。

项目脚本位于 [`package.json`](../../package.json)，Windows 环境要求参见 [项目入门手册](../project_guide.md)。依赖已安装时，在仓库根目录分别启动：

```powershell
pnpm tauri:dev
```

```powershell
pnpm dev:web --host 127.0.0.1
```

通常桌面开发前端使用 `127.0.0.1:6130`，Web 使用 `127.0.0.1:5210/im/`；以实际启动输出为准。首次依赖优化完成后再开始记录。若当前环境的 pnpm 不执行预期脚本，记录现象，不自行安装或更换依赖；可在依赖已存在时使用 `node .\node_modules\vite\bin\vite.js --mode web --host 127.0.0.1` 运行 Web。桌面必须运行真实 Tauri 应用，不能把在浏览器打开桌面页面当作桌面端测试。

Web 邮件入口只接受可信邮箱来源的单次登录地址。正式构建默认使用当前页面来源；若邮箱的公开 `APP_URL` 确实不同，构建时必须设置 `VITE_WEB_MAIL_ORIGIN` 为该邮箱的完整来源（协议、主机和可选端口，不含路径）。Web 开发模式默认信任 `VITE_WEB_PROXY_TARGET` 对应的来源；如果代理目标与公开邮箱来源不同，也应显式设置 `VITE_WEB_MAIL_ORIGIN`。来源配置错误会阻止打开邮件并显示错误，而不会跳转到未受信主机。

两种 Vite 模式可能争用依赖优化缓存；同机优先分时运行，切换模式后重新启动并等待优化完成。真实手机不能访问电脑的 `127.0.0.1`；使用用户提供的安全、已授权的测试部署地址，不擅自暴露开发服务器或将地址改为生产环境。涉及摄像头、麦克风和部分浏览器能力时，还需确认安全上下文与设备权限。

## 执行顺序与状态

1. A、B 完成 [交接协议](handoff.md)，对齐版本、修复、环境、权限和本轮编号。
2. 按 [用例](test-cases.md) 顺序建立私聊及测试群，再覆盖消息、媒体、通话、异常和扩展功能。每个适用的端组合都要单独记录，不因一次成功推断其他组合通过。
3. 双机用例按“准备、双方就绪、执行、双方确认、记录、收尾”协作。若 B 尚未同步结果，A 的观察不能代替 B 的观察。
4. 状态只使用 **未执行、通过、失败、阻塞、不适用**。缺少行等同未执行；缺设备、网络故障、费用或权限不足属于阻塞，不是不适用。不适用仅用于有证据证明该功能对该平台确不提供的实例，并写明依据。
5. A 按证据汇总缺陷，双方继续完成测试。不能在遇到首个问题时擅自切换到修复阶段。
6. **进入修复的门槛：** 所有适用必测实例均有 A/B 所需结果，未执行和阻塞均为零，失败项已登记；不适用均有依据。未满足时暂停修复，并向用户报告阻塞。只有用户明确更改规则后才能例外。
7. 满足门槛后再按严重程度组织修复、添加回归测试，并在相同端和双机组合复测；最终清理测试数据并记录结果。

此前测试发现的头像翻译、请求超时及令牌分类、分屏恢复、后台文件上传调度等问题，均需在本轮基线上重新验证。此前服务不稳定和 WebSocket 异常仍需核查；不能声称已定位或已修复。旧测试报告不替代本轮证据。
